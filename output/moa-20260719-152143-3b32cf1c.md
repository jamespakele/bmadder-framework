# BMADder → Hermes Integration Plan

**Document:** `docs/bmad-hermes-integration-plan.md`  
**Status:** Ready for implementation  
**Architecture:** Passive observer (Hermes mirrors BMADder state, never controls it)

---

## Executive Summary

This plan integrates Hermes Kanban as a **read-only visibility layer** for the BMADder pipeline. The BMADder Rust binary remains the sole owner of story state, git operations, and loop control. A Python bridge script observes BMADder's story files and activity logs, then mirrors that state into Hermes Kanban for human visibility and Telegram alerts.

**Core invariant:** BMADder produces state. Hermes observes and displays that state. [nemotron, qwen35, deepseek, minimax — consensus]

---

## 1. Observer Architecture

```text
bmadder binary (Rust)
  ├─ Owns SM → PO → Dev → QA loop
  ├─ Owns state transitions, retries, frozen specs, git commit/push, resume
  ├─ Writes story frontmatter (docs/backlog/stories/story-*.md)
  ├─ Writes _bmad/logs/activity.log and _bmad/progress.txt
  └─ Fully functional with Hermes absent

bmadder-kanban-bridge.py (deterministic observer)
  ├─ Reads story files + logs only (never writes to them)
  ├─ Creates one Hermes Kanban task per story file
  ├─ Mirrors story status → Kanban task state
  ├─ Adds timeline comments from activity.log
  ├─ Reports role/model/skill metadata for human visibility
  └─ Sends Telegram only for meaningful alerts

Hermes Kanban
  └─ Visibility/reporting layer only; never controls bmadder
```

**Why this architecture:** Two LLM-driven loop control attempts (`delegate_task` and CLI-based Hermes profile invocation) both failed in practice. LLMs cannot sustain structured multi-phase loops with proper wait boundaries. BMADder's Rust `iterative`/`cycle` modes are proven and deterministic. [qwen35, deepseek — consensus]

**Core invariant:** The bridge must **never** edit story files, invoke BMADder, manage retries, dispatch agents, run git, or use `delegate_task` to advance story state. [nemotron, qwen35, deepseek, minimax — consensus]

## 2. Story Status → Kanban Status Mapping

Story frontmatter is authoritative. The bridge translates `status` values to Hermes Kanban task statuses:

| BMADder Story Status | Hermes Kanban Status | Meaning |
|---|---|---|
| `DRAFT` | `todo` | Created/refined by SM |
| `REVISE` | `triage` | PO rejection; SM revision required |
| `READY_FOR_DEV` | `ready` | PO approved; waiting for Dev |
| `IN_DEV` | `running` | Development in progress |
| `PENDING_QA` | `review` | Awaiting QA |
| `REFIX` | `triage` | QA failed; returned to Dev |
| `COMPLETED` | `done` | QA passed or concerns accepted; BMADder committed/pushed |

**Source of truth:** `bmadder-core/src/story.rs` — `StoryStatus` enum with 7 variants. The mapping uses exact BMADder enum variant labels (e.g., `"DRAFT"`, `"READY_FOR_DEV"`). Both `REVISE` and `REFIX` map to `triage`. [nemotron, qwen35, deepseek, minimax — consensus]

Kanban task assignment is display metadata only. Do not dispatch cards to workers. [consensus]

## 3. Activity Log Parsing

BMADder writes two log formats to `_bmad/logs/activity.log`. The bridge must parse both and ignore malformed lines without crashing. [consensus]

### Pipe format (BMADder framework default)

```text
2026-07-16T19:00:00Z | ORCH | STORY-0023 | IN_DEV | dev via kimi-k2.7-code
```

**Fields:** `timestamp | actor | story_id | event | detail`

### Bracket format (current ai-r3 logs)

```text
[2026-07-16T19:00:00Z] ORCH STORY-0023 IN_DEV: dev via kimi-k2.7-code
```

**Fields:** `[timestamp] actor story_id event: detail`

Useful events to surface as Kanban comments:
- `IN_DEV → PENDING_QA` — transition events
- `QA PASS / QA FAIL → REFIX` — QA outcomes
- Role and model detail strings (e.g., `dev via kimi-k2.7-code`)
- `STALLED` events

## 4. Bridge State File (Idempotent Restart)

The bridge maintains checkpoint state in `_bmad/kanban-bridge-state.json` inside the project directory. This ensures restart is idempotent — no duplicate cards, no duplicate comments. [consensus]

> **Divergence note:** All models agree the file lives in the project's `_bmad/` directory. The concrete example path `~/1-projects/ai-projects/ai-r3/_bmad/kanban-bridge-state.json` [qwen35, deepseek] is the runtime location for the ai-r3 project, but the general rule is `{project_root}/_bmad/kanban-bridge-state.json`.

### Schema

```json
{
  "version": 1,
  "board": "ai-r3",
  "last_poll": "2026-07-19T14:30:00Z",
  "activity_log_offset": 12345,
  "stories": {
    "STORY-0023": {
      "kanban_task_id": "task-uuid-here",
      "last_status": "IN_DEV",
      "last_qa_status": null,
      "last_comment_fingerprint": "sha256-of-last-comment"
    }
  }
}
```

### Fields

| Field | Type | Purpose |
|---|---|---|
| `version` | int | Schema version for future migrations |
| `board` | string | Hermes Kanban board name (e.g., `"ai-r3"`) |
| `last_poll` | ISO8601 | Last successful poll timestamp [qwen35] |
| `activity_log_offset` | int | Byte offset into `activity.log` for tail-only new lines |
| `stories` | object | Per-story tracking: Kanban task ID, last mirrored status, QA status, comment dedup fingerprint |
| `last_comment_fingerprint` | string | SHA256 of last appended comment text; avoids duplicate comments on restart |

**Persistence rule:** Write state file after every successful poll cycle. Use atomic write (temp file + rename) to prevent corruption. [qwen35, minimax — consensus]

**Corruption handling:** If the state file is corrupted (invalid JSON), log a warning, delete the corrupted file, and start fresh without crashing. [qwen35]

## 5. Two-Phase Implementation

### Phase 1: Python Bridge Script (Zero BMADder Changes)

**Goal:** Deliver a working observer that reads existing BMADder files (no modifications to BMADder source code). The bridge runs as a standalone Python process, polling the project directory. [consensus]

**Deliverable:** `~/3-resources/config-notes/hermes/bmadder-kanban-bridge.py`

**Responsibilities:**

1. Create/use one Hermes Kanban board per project
2. Poll `docs/backlog/stories/story-*.md` every N seconds (default 10s)
3. Parse YAML frontmatter and extract: `story_id`, `title`, `status`, `po_alignment`, `qa_status`
4. Create one Kanban task per unseen `story_id` using `hermes kanban create --idempotency-key`
5. On status change: update existing task's state and add comment
6. Tail only newly appended `activity.log` bytes (from `activity_log_offset`)
7. Add concise timeline comments to matching story task
8. On `COMPLETED`: complete Kanban task with QA status/commit info if available
9. Send Telegram for meaningful events only:
   - BMADder run started
   - Story committed/pushed
   - Stalled/escalated loop
   - All stories completed

**BMADder read-only data sources:**

| BMADder Source | Bridge Use |
|---|---|
| `docs/backlog/stories/story-*.md` | Story frontmatter (status, title, story_id, qa_status, po_alignment) |
| `_bmad/logs/activity.log` | Timeline events for Kanban comments |
| `_bmad/progress.txt` | Run-level context (START/END markers, ALL_DONE detection) |
| `bmadder.toml` | Optional: role/model metadata for display |

**Reference:** `bmadder-cli/src/ui.rs` — `stories_payload()` and `status_payload()` functions show exactly what data to extract. [qwen35, deepseek]

### Phase 2: Optional JSONL Event Hooks (BMADder Rust Changes)

**Goal:** Improve parsing reliability and reduce bridge polling latency by emitting structured JSONL events from BMADder. This is **optional** — Phase 1 must work independently. [consensus]

**When Phase 2 is appropriate:**
- The Python bridge correctly mirrors all status transitions
- BMADder's activity log format is stable and reliable
- A specific integration benefit justifies modifying BMADder source

**Approach:** Add a `--jsonl-events` CLI flag to BMADder. When enabled, BMADder writes structured events to `_bmad/logs/events.jsonl` alongside the existing activity log. [qwen35, deepseek]

> **Divergence note:** There is minor disagreement on the JSONL event file path. nemotron proposes `_bmad/events.jsonl`; qwen35, deepseek, and minimax propose `_bmad/logs/events.jsonl` or `_bmad/logs/bmadder-events.jsonl`. The majority favor placing it in the logs directory for consistency with `activity.log`. **Decision:** Use `_bmad/logs/events.jsonl`.

**Event schema:**

```jsonl
{"ts":"2026-07-19T14:30:00Z","actor":"ORCH","story_id":"STORY-0023","event":"STATUS_CHANGE","from":"DRAFT","to":"READY_FOR_DEV","detail":"PO approved"}
{"ts":"2026-07-19T14:35:00Z","actor":"DEV","story_id":"STORY-0023","event":"DEV_START","model":"ollama/kimi-k2.7-code:cloud","detail":"Iteration 1/10"}
{"ts":"2026-07-19T14:40:00Z","actor":"QA","story_id":"STORY-0023","event":"QA_PASS","model":"ollama/glm-5.2:cloud","detail":"All 7 AC passed"}
{"ts":"2026-07-19T14:45:00Z","event":"RUN_COMPLETE","completed":5,"stalled":0,"total":5}
```

Event types: `STATUS_CHANGE`, `QA_PASS`, `QA_FAIL`, `STORY_COMPLETE`, `STALLED`, `RUN_START`, `RUN_COMPLETE`. [minimax, deepseek]

**Bridge benefit:** Parse JSONL instead of regex-matching two log formats. Reduces bridge complexity and parsing errors. When JSONL mode is enabled, the bridge tracks offset by **line number** instead of byte offset. [qwen35]

**Priority:** Low. Phase 1 must succeed first. Phase 2 is optimization only. [consensus]

## 7. Hermes Kanban CLI Usage

The bridge uses the `hermes` CLI for all Kanban operations. All commands use `--json` where available for structured output. [minimax, consensus]

```bash
# Board setup (one-time, idempotent)
hermes kanban boards create ai-r3 \
  --name "ai-r3 BMAD Stories" \
  --description "Passive mirror of bmadder story state" \
  --switch

# Card creation (with idempotency key)
hermes kanban create "STORY-0023: Implement bridge core" \
  --body "<summary>" \
  --idempotency-key "bmadder:ai-r3:STORY-0023" \
  --json

# Status update
hermes kanban status <task_id> <kanban_status>

# Comment (with author attribution)
hermes kanban comment <task_id> "DRAFT → READY_FOR_DEV · PO approved" \
  --author bmadder-bridge

# Completion (with metadata)
hermes kanban complete <task_id> \
  --result "QA PASS; bmadder committed and pushed" \
  --metadata '{"story_id":"STORY-0023","qa_status":"PASS","commit":"abc123"}'

# Blocking (for stalled stories)
hermes kanban block <task_id> \
  --kind needs_input \
  "bmadder reported a stalled story"
```

**Idempotency key format:** `bmadder:<board>:<story_id>` (e.g., `bmadder:ai-r3:STORY-0023`). [consensus]

### Story Card Body Content

Each Kanban card body should include:

```markdown
**BMADder Story:** STORY-0023
**Source:** `docs/backlog/stories/story-0023-*.md`

- Status: `IN_DEV`
- PO alignment: `aligned`
- QA status: `null`
- Acceptance criteria: 3/7 complete
```

The card body is updated on each status change. Reference: `bmadder-cli/src/ui.rs` — `stories_payload()`. [minimax, qwen35]

## 8. Telegram Notification Triggers

Send a Telegram message **only for meaningful events**. Do not send Telegram for routine status transitions (e.g., DRAFT→REVISE, IN_DEV→PENDING_QA). [consensus]

| Event | Message Template |
|---|---|
| Bridge started | `🚦 bmadder-bridge started for <board>` |
| BMADder run started | `🔄 BMADder run started · <board> · <timestamp>` |
| Story committed/pushed | `✅ <story_id>: <title> — COMPLETED. QA: <qa_status>. Commit: <commit_hash>` |
| Story stalled | `⚠️ <story_id>: STALLED after max iterations` |
| All stories completed | `🎉 All stories in <board> COMPLETED (<count> stories)` |

Use the existing Hermes gateway for Telegram. No raw environment variables needed. [minimax, qwen35]

## 9. Acceptance Criteria

### Phase 1 — Python Bridge

**AC-1: Story discovery and card creation**
- **Given** BMADder has story files in `docs/backlog/stories/story-*.md`
- **When** the bridge script starts with project path and board name
- **Then** exactly one Hermes Kanban task is created per story file using `--idempotency-key "bmadder:<board>:<story_id>"`
- **And** each task's state matches the story's frontmatter status per the status mapping
- **And** the task contains the story title in its name

**AC-2: Status mirroring**
- **Given** a story file's `status` field changes from `DRAFT` to `READY_FOR_DEV`
- **When** the bridge detects the change on next poll
- **Then** the corresponding Kanban task's status updates to `ready`
- **And** a comment is added containing the latest activity log entry for that story
- **And** the comment includes the actor, event, and detail from the log line

**AC-3: No duplicate cards on restart**
- **Given** the bridge was running and created tasks for all existing stories
- **When** the bridge is restarted after a crash
- **Then** no duplicate tasks are created (idempotency key prevents duplicates)
- **And** it resumes monitoring from the last recorded `activity_log_offset`
- **And** it preserves all existing Kanban task states and comments

**AC-4: Activity log tailing**
- **Given** BMADder writes new lines to `_bmad/logs/activity.log`
- **When** the bridge polls
- **Then** only new lines (from byte offset) are parsed (both pipe and bracket formats)
- **And** concise comments are added to the matching story task
- **And** log lines containing role/model info include `"Role: BMADder Developer · Model: Kimi K2.7 Code"` in the comment

**AC-5: COMPLETED handling**
- **Given** a story reaches `COMPLETED` with `qa_status: "PASS"`
- **When** the bridge polls
- **Then** the Kanban task is completed with result `"QA PASS; bmadder committed and pushed"`
- **And** metadata includes `{"story_id":"STORY-0023","qa_status":"PASS"}`

**AC-6: Telegram on meaningful events**
- **Given** a story transitions to `COMPLETED` and BMADder commits/pushes
- **When** the bridge processes the status change
- **Then** a Telegram message is sent with story ID, title, and commit hash
- **Given** all stories are `COMPLETED`
- **When** the bridge detects `ALL_DONE` in `progress.txt`
- **Then** a Telegram completion message is sent with total story count

**AC-7: Malformed log line handling**
- **Given** the bridge encounters a malformed line in activity log
- **When** parsing the log for new entries
- **Then** it skips the line without crashing
- **And** it continues processing subsequent valid lines
- **And** it logs a warning to stderr (but does not halt)

**AC-8: BMADder unchanged**
- **Given** BMADder is running in the project directory
- **When** the bridge is started or stopped
- **Then** no BMADder files are modified, no git operations occur, no BMADder processes are affected

### Phase 2 — JSONL Event Hooks

**AC-9: Structured events emitted**
- **Given** `--jsonl-events` is enabled
- **When** a story status changes
- **Then** a structured JSON event is written to `_bmad/logs/events.jsonl` with fields: `ts`, `actor`, `story_id`, `event`, `from`, `to`, `detail`

**AC-10: Bridge reads JSONL when present**
- **Given** JSONL events are present in `_bmad/logs/events.jsonl`
- **When** the bridge runs
- **Then** it processes JSONL events with higher priority than activity log parsing
- **And** no regex parsing is required for event extraction

**AC-11: Graceful degradation**
- **Given** JSONL file is absent or malformed
- **When** the bridge runs
- **Then** it falls back to activity log parsing without error

**AC-12: JSONL disabled by default**
- **Given** `--jsonl-events` is disabled (default)
- **When** BMADder runs
- **Then** no `events.jsonl` file is created

## 10. Hard Non-Responsibilities

These are architectural constraints — not preferences. Any bridge behavior that violates these must be reverted immediately. [consensus]

1. **Never modify story frontmatter or body** — the bridge is read-only on `docs/backlog/stories/`
2. **Never modify files in `_bmad/`** except its own state file `_bmad/kanban-bridge-state.json`
3. **Never run `git`** — no commits, no pushes, no branch operations
4. **Never launch or control BMADder** — no subprocess spawning of `bmadder`
5. **Never retry or unblock a story** — if a story stalls, bridge reports it via Telegram; it does not attempt fixes
6. **Never dispatch Kanban tasks to workers** — Kanban cards are display-only mirrors
7. **Never use `delegate_task` to advance loop state** — LLM-driven loop control has failed twice
8. **Never use Hermes profiles to advance story state** — profiles may be used for one-shot observations only
9. **Never modify `ai-hi-lit/`** — it is read-only reference for deployed skills
10. **Never write to the Kanban SQLite DB directly** — always use the Hermes CLI
11. **Never alter story frontmatter fields** (`status`, `po_alignment`, `qa_status`, etc.)
12. **Never change the meaning of existing BMADder statuses**
13. **Never assume exclusive access to story files** — handle concurrent reads safely

## 14. Risk Mitigation

| Risk | Mitigation |
|---|---|
| Activity log format changes | Bridge ignores malformed lines; Phase 2 JSONL provides stable schema |
| Hermes Kanban CLI changes | Bridge calls CLI via subprocess; version-gate critical commands |
| Story files modified during poll | Bridge reads all stories, computes diff, updates Kanban in one pass |
| Bridge state file corrupted | Catch JSON decode errors, log warning, reinitialize from current state |
| Telegram gateway unavailable | Catch send errors, log warning, continue polling |
| BMADder runs faster than poll interval | Bridge detects all changes on each poll; no event loss from polling interval alone |
